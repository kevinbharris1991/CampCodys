Scope and readiness

This is an API foundation, not a certified electronic health record, payment processor, or complete camp management product. It supplies authentication, database-backed group membership, a resource permission matrix, scoped CRUD, and guest meal/activity views. Clinical review, privileged-operator MFA/identity-provider integration, business approvals, operational monitoring, and independent security testing are production prerequisites. Self-registered accounts use mandatory native TOTP; existing operator accounts retain their existing sign-in behavior.

HIPAA compliance is an organizational responsibility, not a property guaranteed by this code. Do not load real protected health information (PHI) until the deployment safeguards below are in place. No code or hosting vendor can establish compliance merely by calling an API “secure.”

Authentication

Base URL: https://your-camp-host/api/v1. All requests require an API client token and secret. Provision credentials using the trusted CLI; do not embed shared secrets in public JavaScript or ship a shared production secret inside mobile binaries. Use a trusted application gateway for mobile/browser deployments. Mobile samples show the HTTP contract only; supply short-lived, appropriately provisioned credentials through your secure architecture.

X-API-Token: <client token>
X-API-Secret: <client secret>
Accept: application/json
Content-Type: application/json

Sign in with POST /auth/login:

{"email":"guest@example.org","password":"<user password>"}

The email field also accepts a self-registered account's username (case-insensitive). Existing operator accounts receive access_token and expires_in. MFA accounts instead receive only {"mfa_token":"<token>"}; send {"mfa_token":"<token>","code":"123456"} to POST /auth/mfa/verify to obtain the session. MFA challenges expire after five minutes, are single-use and bound to the API client and current password. For subsequent authenticated requests also send Authorization: Bearer <access_token>. The client credentials alone do not grant user permissions. Treat bearer tokens as secrets; never put any credentials in query strings, analytics, crash reports, or logs.

GET /auth/me returns the signed-in user, assigned groups, and effective permissions. Permissions are additive across memberships, with record scopes enforced on every operation. Signing out via POST /auth/logout revokes the current session. Handle HTTP 401 by signing in again; do not retry passwords automatically.

Guest self-registration

All stages still require the API client headers. No user session is created until email activation, profile completion, and authenticator verification have all succeeded. Public registration accepts no role, membership, owner or user ID fields; it creates only a Guest membership. Only trusted operators may grant staff access.

  1. POST /auth/register with exactly: 
    {"name":"Alex Example","date_of_birth":"1996-04-15","email":"alex@example.org",
 "gender":"prefer_not_to_say","terms_accepted":true,"privacy_accepted":true}
    Name is nonempty text up to 120 characters; gender must be one of female, male, non_binary, self_described or prefer_not_to_say. Date of birth is a real YYYY-MM-DD date on or after 1900-01-01. Registrants must be 13 or older, including on their thirteenth birthday (UTC); the API rejects younger users even if browser validation is bypassed. Each acceptance must independently be the JSON boolean true; separate acceptance timestamps are retained. The response is always the same eligibility-neutral {"message":"..."} for valid new or duplicate addresses. For an incomplete account, re-registration sends a fresh activation/recovery link without changing stored demographics, consent, username, password or authenticator. Existing unconsumed email links remain valid until their own expiry or a successful activation; an unauthenticated sender cannot invalidate an earlier email link or reset established credentials. Completed accounts receive the same generic response but no enrollment link. Requests are limited to three per address per hour and ten per network address per hour.
  2. The configured PHP mail transport sends a 24-hour link to the fixed configured portal origin: https://your-camp-host/public/?activate=<token>. The portal submits {"token":"<token>"} to POST /auth/activate. The single-use activation token is exchanged for {"onboarding_token":"<token>","next_step":"profile"}, or next_step:"mfa" when recovering an already-established profile. For mfa, call /auth/mfa/setup with the new onboarding token and show the existing authenticator setup; do not submit a new profile or password. Successful activation invalidates sibling activation links and any previous onboarding capability. The onboarding capability expires after 24 hours and is bound to the API client used for activation; it never authorizes record/session endpoints. Keep it only in protected server-side portal session storage. If the browser session is lost or expires, use the registration form again and follow the newly emailed recovery link.
  3. POST /auth/profile: 
    {"onboarding_token":"<token>","username":"alex.example",
 "password":"<12-1024 byte password>","password_confirmation":"<same password>"}
    Username is case-insensitive and 3–40 ASCII letters, digits, dots, underscores or hyphens, starting with a letter or digit; email-style usernames are not allowed. Conflicting usernames return 409. Passwords are Argon2id-hashed and cannot contain null bytes. Optionally add profile_picture containing canonical raw base64 JPEG or PNG (no data-URL prefix), decoded size at most 256 KiB, each dimension at most 4096 pixels, and at most 16 million pixels. Omit the property when absent. This endpoint alone permits a 768 KiB JSON body to accommodate base64 and slash escaping; other bodies remain limited to 64 KiB. The response is {"mfa_secret":"<base32>","mfa_uri":"otpauth://totp/..."}. Retain the unchanged onboarding token. Profile submission is one-time and cannot replace a username, password or authenticator after establishment.
  4. For reload/retry, send {"onboarding_token":"<token>"} to POST /auth/mfa/setup. Only the profile-complete, not-yet-confirmed stage can retrieve the same mfa_secret and mfa_uri. Display these privately for manual entry into a compatible authenticator. Do not send the secret to third-party QR services.
  5. POST /auth/mfa/confirm with {"onboarding_token":"<token>","code":"123456"} validates the authenticator and atomically creates the Guest account and session: {"access_token":"<token>","expires_in":3600}. The onboarding token is then invalidated. Proceed to the dashboard using GET /auth/me. All later password logins require /auth/mfa/verify.

TOTP uses a random 160-bit secret, HMAC-SHA1, six digits and 30-second periods, accepting at most one period of clock skew. Each accepted time step is recorded under a transaction lock; a code cannot be reused for another session, including the enrollment code. If signing in immediately after setup, wait for the authenticator's next code. There are no email-only sessions, recovery-code bypasses, public password resets, or public MFA disabling. Lost-factor recovery requires a separately reviewed operator identity-verification process.

Registration deployment and upgrades

Read APP_PUBLIC_URL and APP_MAIL_FROM from the process environment (takes precedence) or protected root .env. The URL must be absolute, with the exact path /public/, no user information, query or fragment, and HTTPS in production. The sender must be a valid email without header control characters. Neither activation links nor mail headers are derived from request Host/forwarded headers or submitted origins. Leave both unset to preserve legacy sign-in while registration returns 503. Configure PHP's native mail() transport using server-level sendmail_path or platform SMTP settings; there is no development-token response or production test-mail bypass. Monitor delivery, configure SPF/DKIM/DMARC and protect mail infrastructure. An accepted transport handoff does not guarantee mailbox delivery.

The portal separately requires PORTAL_TERMS_URL and PORTAL_PRIVACY_URL to point to your published policies. Like its existing PORTAL_API_* credentials, these portal settings must be set in the portal process environment, not only in .env. Without both valid policy URLs, the portal hides the registration form rather than requesting acceptance of missing policies.

Existing installations must rerun php bin/console.php setup with the migration identity before deploying new code. Schema changes are additive: account_onboarding, onboarding_activation_tokens and mfa_challenges; existing users and memberships are not migrated or changed. Grant the runtime account SELECT/INSERT/UPDATE/DELETE on all three new tables and INSERT on users/memberships for final Guest creation, in addition to existing runtime grants. Keep role-management policy CLI-only and deny runtime UPDATE/DELETE on audit_events. Schedule php bin/console.php cleanup to remove expired activation links, challenges, and existing expired operational data. Incomplete encrypted registrations remain recoverable until their onboarding capability has been expired for over 30 days; cleanup then removes them only when no unexpired recovery link exists. This bounded recovery-retention window does not extend token validity. Completed encrypted profiles, consent dates, and MFA secrets are retained; establish an approved retention and recovery policy.

Name, birth date, gender, photo and TOTP secrets are encrypted with the application key using authenticated sodium secretbox encryption. The public display name for new accounts is their username; email, username, consent timestamps and ownership/stage metadata are not encrypted. Activation/onboarding/challenge/session capabilities are stored only as SHA-256 hashes, expire, and are invalidated on successful consumption. Registration, activation, profile and MFA endpoints are throttled independently; failed MFA attempts are counted outside rollback-able transactions. Password changes, membership changes, session revocation, disabling users and revoking clients invalidate pending MFA login challenges.

Endpoint reference

POST /auth/register
Validated initial profile and separate terms/privacy acceptance; generic response, activation by email.
POST /auth/activate
Exchange a single-use activation token for an expiring onboarding token.
POST /auth/profile
One-time username/password/photo establishment; returns private TOTP setup details.
POST /auth/mfa/setup
Resume the same pending authenticator setup using the unchanged onboarding token.
POST /auth/mfa/confirm
Confirm enrollment and atomically create a Guest session.
POST /auth/login
Client credentials plus email-or-username/password; legacy session or expiring MFA challenge.
POST /auth/mfa/verify
Single-use MFA challenge and fresh six-digit authenticator code; creates a session.
GET /auth/me
Current user, database memberships, effective permissions.
POST /auth/logout
Revokes the presented bearer token.
GET /resources
Authorized resource schemas and permitted operations. Use this as the live field reference.
GET /records/{resource}
List accessible records. The server applies ownership/assignment scopes. Optional positive-integer query parameters: after (cursor), limit (default 50, maximum 100), camper_id (narrows results, never grants access).
GET /records/{resource}/{id}
Read one accessible record.
POST /records/{resource}
Create a record using the resource schema.
PATCH /records/{resource}/{id}
Update permitted fields. Membership and ownership cannot be changed by editing a record.
DELETE /records/{resource}/{id}
Delete only where explicitly permitted. Follow deployment retention policies.
GET /menus?camper_id={id}
Meal view matched against the authorized camper's disclosed allergies/sensitivities. Without a camper ID the result is not assessed. Read the camper's special meals separately through GET /records/special_meals?camper_id={id}.
GET /activities
Guest-visible activities/events, not internal schedules.
POST /activities/{id}/signup
Enroll an authorized camper in an available activity. Body: {"camper_id":42}. The API checks ownership, duplicate signup, availability and capacity.

Record endpoints use a data envelope in responses. IDs are positive integers. Unsupported methods, unknown resources, unknown fields, and malformed JSON are rejected. Errors are JSON and do not echo submitted health data.

Common statuses: 400 invalid request; 401 missing/invalid client credentials or session; 403 forbidden; 404 unknown or inaccessible record; 405 unsupported method; 409 conflicting state, full activity or duplicate signup; 413 body too large; 415 expected JSON content type; 422 invalid fields/query; 429 throttled; 500/503 service/configuration failure. Do not infer record existence from forbidden/not-found responses. Never show raw exceptions to end users.

Group and scope model

Membership is managed by trusted operators. There is no unrestricted “superuser” bypass. Administrative role assignment and credential recovery are intentionally CLI-controlled in this foundation; the portal cannot grant itself access.

Executive readers can use GET /records/audit_events and GET /records/configuration for sanitized, read-only operational information. Configuration never returns secrets. Audits contain event metadata, not clinical content.

Dietary staff use GET /records/camper_names (or /{id}) to cross-reference meals. This projection returns only camper ID and display name, not the broader camper record or clinical history.

Guests discover grants through GET /records/grant_opportunities (or /{id}), which returns only id, name and optional application_instructions. The finance grants ledger remains inaccessible. Finance publishes opportunities by setting application_status to available; grants default to internal and can be closed. Use the catalog ID as grant_id in an application. Closed/internal grants cannot receive new guest applications, while authorized reviewers can finish existing applications after closure.

  1. Executive Director: configuration/audit visibility and aggregate camper reporting; financial approvals, budgets/grants, and public/mission content. No raw clinical records.
  2. Administrative Directors: administrative intake, consent/waivers, household demographics, rosters/cabins, policies, onboarding, templates and compliance reports. Trusted CLI handles account/role changes.
  3. Medical & Nursing Staff: medications, medication administration, health profiles/protocols, and clinical incidents; no public content, finance or role settings.
  4. Behavioral Support Services: support plans, behavioral tracking and counselor strategies, plus separately curated behavior-relevant health context; not full clinical records.
  5. Accessibility & Adaptive Services: accommodations, adaptive equipment, facility audits and accessibility work requests.
  6. Program Directors: master activities, adaptation guidance, participation, and separately curated safety alerts; no full clinical history.
  7. Counselors & DSP's: assigned campers' care profiles and daily logs; incident submission only. No global schedule, billing, or plan editing.
  8. Facilities & Cabin Maintenance: work orders, inspections and emergency alerts. No camper personal, clinical or behavioral records.
  9. Housekeeping: sanitation rosters, sensory-room setup and supply requests; no camper records.
  10. Catering & Dietary Support: dietary restrictions, menu planning and special meals; no general health or behavioral records.
  11. Finance & Accounting: billing, payroll, grant funds and financial reporting; no clinical or behavioral records.
  12. Guest: own reservations, accommodations, prescription disclosures, allergies, grant applications and activity signups; read guest-facing menus/events, own balances and own special meals only.

“Read only” does not imply unrestricted access. A counselor's reads are assignment-scoped; a guest's reads and writes are owner-scoped. Users with several groups receive the union of their explicitly granted capabilities. Assign only necessary groups and regularly review combinations.

Working with records

Fetch GET /resources first. It is the authoritative list of resource names, fields and operations for the caller. Do not guess resource names or place arbitrary JSON into records. Separate clinical, behavioral, safety, care and dietary resources prevent broad records from being returned to roles needing only a subset.

GET /api/v1/resources
GET /api/v1/records/reservations
GET /api/v1/records/reservations/42

Before creating or updating, use the exact field schema advertised by the API. An owner or camper link is an authorization boundary, not a client-trusted assertion. Guests cannot select another owner; counselors cannot select an unassigned camper. Only trusted operators manage counselor assignments and memberships.

Example: a guest reservation

Use a camper ID already linked to this guest by a trusted operator. Send fields directly in the JSON object, not inside a data wrapper:

POST /api/v1/records/reservations
Content-Type: application/json

{
  "camper_id": 42,
  "arrival_date": "2027-06-07",
  "departure_date": "2027-06-14",
  "status": "requested"
}

A successful create returns HTTP 201 with a data record containing its ID and fields. To cancel, PATCH /records/reservations/{id} with {"status":"cancelled"}. Guests cannot confirm their own booking or approve their own grant application.

Lists return {"data":[...],"next_after":null}. If next_after is an ID, request the next page using ?after={id}&limit=50. Preserve any camper filter. Single-record responses return {"data":{...}}. Timestamps are UTC. Record requests are limited to 64 KiB, with smaller field-specific limits in the resource schema.

Activity signup automatically creates a participation record for Program Directors. To cancel an enrollment, PATCH its activity_signups record with {"status":"cancelled"}. Recorded attendance cannot be erased through cancellation. Trusted operators preload restricted housekeeping/facility task rosters with the CLI's seed-task command; read/update-only teams cannot manufacture their own tasks.

Clinical staff must curate minimum-necessary safety/behavior/care extracts. The API does not automatically convert a full medical history into a safe summary. Do not copy PHI into public content, menus, schedules, maintenance work orders, housekeeping instructions or financial descriptions. The system cannot detect all inappropriate free-text disclosure.

For meals, use a consistent vocabulary for allergen and sensitivity tags. Matching is a presentation aid, not a guarantee: unknown ingredients, cross-contact, texture requirements, medication interactions and late dietary changes require staff review. The portal strikes through flagged meals and shows the guest's special meal. Do not serve a meal based solely on automated matching.

Reservation balances and billing records are bookkeeping only. Actual payments/refunds must use a compliant external payment processor with tokenized references; never submit card numbers, CVVs, bank credentials or insurance identifiers in free text. Guests can read their own billing records but cannot mark them paid or change amounts. Grant applications are distinct from finance allocation/approval records. A guest's own grant application does not grant access to finance reports.

Client examples

Each example signs in and fetches groups through /auth/me. Replace the base URL with your own TLS endpoint. Credentials come from secure runtime configuration, not source code. The password-only examples below target existing operator accounts; MFA clients must handle the challenge/verify branch documented above before using a bearer session. Examples intentionally do not print passwords, tokens or PHI. Handle production network errors, cancellation, reauthentication and HTTP 429 with bounded backoff.

JavaScript (trusted Node.js server, built-in fetch)

const base = process.env.CAMP_API_BASE;
if (new URL(base).protocol !== "https:") throw new Error("HTTPS required");
const headers = {
  "Content-Type": "application/json",
  "X-API-Token": process.env.CAMP_API_TOKEN,
  "X-API-Secret": process.env.CAMP_API_SECRET
};
async function request(path, options = {}) {
  const response = await fetch(base + path, {
    ...options, headers: { ...headers, ...options.headers },
    redirect: "error", signal: AbortSignal.timeout(15000)
  });
  if (!response.ok) throw new Error(`API status ${response.status}`);
  return response.json();
}
const session = await request("/auth/login", {
  method: "POST",
  body: JSON.stringify({ email: process.env.CAMP_EMAIL,
                         password: process.env.CAMP_PASSWORD })
});
const me = await request("/auth/me", {
  headers: { Authorization: ["Bearer", session.access_token].join(" ") }
});
// Use me.groups in your authorized application view; do not log me.

PHP (server-side cURL)

<?php
function request(string $path, ?array $body = null, ?string $bearer = null): array {
    $headers = ['Content-Type: application/json',
        'X-API-Token: ' . getenv('CAMP_API_TOKEN'),
        'X-API-Secret: ' . getenv('CAMP_API_SECRET')];
    if ($bearer !== null) $headers[] = 'Authorization: Bearer ' . $bearer;
    $ch = curl_init(getenv('CAMP_API_BASE') . $path);
    curl_setopt_array($ch, [
        CURLOPT_HTTPHEADER => $headers, CURLOPT_RETURNTRANSFER => true,
        CURLOPT_TIMEOUT => 15, CURLOPT_FOLLOWLOCATION => false,
        CURLOPT_PROTOCOLS => CURLPROTO_HTTPS
    ]);
    if ($body !== null) {
        curl_setopt($ch, CURLOPT_POST, true);
        curl_setopt($ch, CURLOPT_POSTFIELDS, json_encode($body, JSON_THROW_ON_ERROR));
    }
    $raw = curl_exec($ch);
    $status = curl_getinfo($ch, CURLINFO_RESPONSE_CODE);
    curl_close($ch);
    if ($raw === false || $status < 200 || $status >= 300) {
        throw new RuntimeException('API request failed');
    }
    return json_decode($raw, true, 64, JSON_THROW_ON_ERROR);
}
$session = request('/auth/login', [
    'email' => getenv('CAMP_EMAIL'), 'password' => getenv('CAMP_PASSWORD')
]);
$me = request('/auth/me', null, $session['access_token']);

Python (standard library)

import json
import os
from urllib.request import Request, build_opener, HTTPRedirectHandler

class NoRedirect(HTTPRedirectHandler):
    def redirect_request(self, req, fp, code, msg, headers, newurl):
        return None

opener = build_opener(NoRedirect)
base = os.environ["CAMP_API_BASE"]
if not base.startswith("https://"):
    raise ValueError("HTTPS required")

def request(path, body=None, bearer=None):
    headers = {
        "Content-Type": "application/json",
        "X-API-Token": os.environ["CAMP_API_TOKEN"],
        "X-API-Secret": os.environ["CAMP_API_SECRET"],
    }
    if bearer:
        headers["Authorization"] = "Bearer " + bearer
    payload = None if body is None else json.dumps(body).encode()
    req = Request(base + path, data=payload, headers=headers,
                  method="GET" if body is None else "POST")
    with opener.open(req, timeout=15) as response:
        return json.load(response)

session = request("/auth/login", {
    "email": os.environ["CAMP_EMAIL"],
    "password": os.environ["CAMP_PASSWORD"],
})

Java (Android, platform APIs)

Run off the main/UI thread. Add the Android INTERNET permission. Do not enable cleartext traffic. The parameters below must come from your secure gateway/session provisioning flow; do not hardcode a shared application secret.

import org.json.JSONObject;
import javax.net.ssl.HttpsURLConnection;
import java.net.URL;
import java.io.InputStream;
import java.io.ByteArrayOutputStream;
import java.nio.charset.StandardCharsets;

static JSONObject request(String base, String path, String clientToken,
        String clientSecret, JSONObject body, String bearer) throws Exception {
    HttpsURLConnection c = (HttpsURLConnection) new URL(base + path).openConnection();
    c.setInstanceFollowRedirects(false);
    c.setConnectTimeout(15000);
    c.setReadTimeout(15000);
    c.setRequestMethod(body == null ? "GET" : "POST");
    c.setRequestProperty("Content-Type", "application/json");
    c.setRequestProperty("X-API-Token", clientToken);
    c.setRequestProperty("X-API-Secret", clientSecret);
    if (bearer != null) c.setRequestProperty("Authorization", "Bearer " + bearer);
    try {
        if (body != null) {
            c.setDoOutput(true);
            try (java.io.OutputStream out = c.getOutputStream()) {
                out.write(body.toString().getBytes(StandardCharsets.UTF_8));
            }
        }
        if (c.getResponseCode() < 200 || c.getResponseCode() >= 300)
            throw new java.io.IOException("API request rejected");
        try (InputStream in = c.getInputStream();
             ByteArrayOutputStream out = new ByteArrayOutputStream()) {
            byte[] buffer = new byte[4096];
            int n;
            while ((n = in.read(buffer)) != -1) out.write(buffer, 0, n);
            return new JSONObject(new String(out.toByteArray(), StandardCharsets.UTF_8));
        }
    } finally { c.disconnect(); }
}

// Inside your background executor, with securely supplied variables:
JSONObject credentials = new JSONObject().put("email", email).put("password", password);
JSONObject session = request(base, "/auth/login", clientToken, clientSecret, credentials, null);
JSONObject me = request(base, "/auth/me", clientToken, clientSecret, null,
                        session.getString("access_token"));

Swift (iOS, URLSession async/await)

Use a gateway for production client credentials. Retain a user session in Keychain only when persistence is needed. Keep App Transport Security enabled. This example uses an ephemeral session and rejects redirects.

import Foundation

final class NoRedirect: NSObject, URLSessionTaskDelegate {
    func urlSession(_ session: URLSession, task: URLSessionTask,
        willPerformHTTPRedirection response: HTTPURLResponse,
        newRequest request: URLRequest,
        completionHandler: @escaping (URLRequest?) -> Void) {
        completionHandler(nil)
    }
}

struct Login: Decodable { let access_token: String; let expires_in: Int }
struct Group: Decodable { let id: Int; let name: String }
struct Me: Decodable { let groups: [Group] }

func request<T: Decodable>(_ type: T.Type, base: URL, path: String,
    clientToken: String, clientSecret: String,
    body: [String: String]? = nil, bearer: String? = nil) async throws -> T {
    guard base.scheme == "https",
          let url = URL(string: base.absoluteString + path) else {
        throw URLError(.badURL)
    }
    var req = URLRequest(url: url)
    req.timeoutInterval = 15
    req.httpMethod = body == nil ? "GET" : "POST"
    req.setValue("application/json", forHTTPHeaderField: "Content-Type")
    req.setValue(clientToken, forHTTPHeaderField: "X-API-Token")
    req.setValue(clientSecret, forHTTPHeaderField: "X-API-Secret")
    if let bearer { req.setValue(["Bearer", bearer].joined(separator: " "), forHTTPHeaderField: "Authorization") }
    if let body { req.httpBody = try JSONSerialization.data(withJSONObject: body) }
    let session = URLSession(configuration: .ephemeral, delegate: NoRedirect(),
                             delegateQueue: nil)
    defer { session.invalidateAndCancel() }
    let (data, response) = try await session.data(for: req)
    guard let http = response as? HTTPURLResponse, (200...299).contains(http.statusCode)
        else { throw URLError(.badServerResponse) }
    return try JSONDecoder().decode(type, from: data)
}

// From an async function with securely supplied parameters:
let login = try await request(Login.self, base: base, path: "/auth/login",
    clientToken: clientToken, clientSecret: clientSecret,
    body: ["email": email, "password": password])
let me = try await request(Me.self, base: base, path: "/auth/me",
    clientToken: clientToken, clientSecret: clientSecret, bearer: login.access_token)

Deployment and HIPAA safeguards

  • Terminate TLS at a hardened web server. Forward the verified HTTPS state to PHP through trusted server configuration; never trust arbitrary client-supplied forwarding headers. Do not deploy the development HTTP bypass.
  • Expose only the API front controller, portal assets, and static developer page. Block direct access to source modules, SQL, CLI tools, tests, environment files, dotfiles and repository metadata. The PHP development server is not a production web server.
  • Set secrets through a secret manager or protected process environment outside the document root. Use an independent application-encryption key and back it up securely. Losing it makes encrypted records unreadable. Rotation requires a planned decrypt/re-encrypt migration; do not simply replace it.
  • Use a least-privilege runtime MySQL account, a separate migration identity, encrypted DB transport when remote, encrypted disks/backups, tested restore procedures, and restricted network access. Set DB_SSL_CA to the trusted CA certificate for remote production MySQL. Application encryption does not protect all metadata, including account identities and ownership links.
  • Self-registration mandates TOTP, but existing operator accounts retain password-only compatibility. Implement privileged-operator MFA and an approved identity/recovery lifecycle before production PHI access. Review privileged memberships, disable departed users, revoke compromised clients/sessions and rotate secrets through controlled operations.
  • Protect audit storage against runtime alteration using restricted grants and remote immutable retention. Monitor denied access, abnormal reads, login failures, exports, and privileged CLI changes. Audit metadata is still sensitive; do not log request/response bodies, passwords, headers or session tokens.
  • Configure web/proxy access logs to omit query strings and record identifiers, or protect them as sensitive metadata with restricted access and an approved retention policy. REST paths can reveal that a user accessed a health-related resource.
  • Set retention, legal-hold, backup and deletion policies before enabling destructive operations. Use minimum-necessary data, verified guardian relationships and explicit policies for camper access.
  • Obtain applicable business associate agreements, perform a documented risk assessment, train staff, maintain incident response/breach notification procedures, and conduct penetration testing and access reviews.
  • Use endpoint device controls and automatic screen locks. The portal has a 15-minute idle timeout; also configure server-side PHP session garbage collection and restrictive session storage permissions.

No permissive CORS is supplied. Browser applications should use a same-origin trusted backend such as this portal. Any future CORS, reverse proxy, payment, file upload, export, clinical signing or role-management feature needs its own threat review.
